## 1. Answers

**Q1: what is the flag?** `$0300 + scene id` (global index 768-1023, byte `$0A60 + (scene >> 3)`, bit `scene & 7`). It means "the permanent stat reward of this scene has been claimed". `TestFlag_0300` / `SetFlag_0300` (`flag_helpers.asm:210`, `:221`; the `ADC #$0300` is at 46234 / 46245) mask A to 8 bits and add `$0300`, so the argument is the scene id. The 87 scenes with a nonzero tier in `enemy_clear_reward_table` are the only ones whose flag is ever written; the other 169 flags have no writer.

**Q2: what does a reward do?** The tier byte (`enemy_clear_reward_table[scene]`, bank 01, row offset `109278 + scene`) selects: **1 = Max HP +1 (29 scenes), 2 = STR +1 (27), 3 = DEF +1 (31)**; amount always 1. Tiers above 3 do not occur (`StandardEnemyDefeatHandler` would give DEF; `BossClearApplyStatReward` would set the flag and give nothing). HP: `reward_actors.asm` `e_hp_increase` adds 1 to `playerMaxHp` ($0ACA) and sets `hpToHeal` ($0B22) to max HP minus HP (full refill); STR / DEF add 1 to `playerStr` ($0ADE) / `playerDef` ($0ADC). No gems, items or map reveals are given by this system: the gem decision is separate (Q5); the per-enemy field reveal of `StandardEnemyDefeatHandler` (`SpawnFieldRevealEffect`, event flag `$0100 + deathActionIdx`, `StandardEnemyDefeatHandler.asm:117-131`, 56355-56403) is a different mechanism keyed to D3 flags; and the `field_reveal_object` stat-item path that would give items `$80-$82` is never reached (Q6).

**Q3: how is a clear detected?** By counting, not by a flag:
- `InitActorFromSceneData` increments `enemiesRemaining` ($0AEC, hex) and `enemiesRemainingBcd` ($0AEE) for every enemy-spawn row (stats index nonzero) unless the row's enemy number is nonzero and its kill bit in `wramFlags` is already set (`actor_execution.asm:993-1011`, increment at 249750, BCD at 249753-249764; kill-bit skip at 249721). Enemy number 0 is always counted. `ClearSceneState` zeroes both (`scene_lifecycle.asm:817-818`, 253345 / 253348), so every scene entry starts at 0 and counts up while the scene list spawns.
- A kill decrements both and stores the new count in `orbitAngle` ($7F0010,X): `StandardEnemyDefeatHandler` (56202-56242; `orbitAngle` at 56242), `EnemyDefeatDispatch_CountKill` (697463-697481) and the inline copies in `pyCC_mystic_ball` (771896-771918) and `awB1_wall_walker` (770331-770353). The three callers of the dispatch family test `enemiesRemaining == 1` first and JumpFar into `StandardEnemyDefeatHandler` for the last enemy (`EnemyDefeatDispatch.asm:34-43`, `pyCC_mystic_ball.asm:187-194`, `awB1_wall_walker.asm:251-258`), so the last kill always runs through `StandardEnemyDefeatHandler`.
- Death routing: `HitStaggerResolveHit` sets the victim's entry to `StandardEnemyDefeatHandler` unless an `onDeathCallback` exists (`hit_stagger_controller.asm:269-275`, offsets 55740-55758).
- Last enemy = `orbitAngle` 0 after the decrement (`DefeatDieOrReward`, 56404: nonzero dies, zero jumps to `EnemyStatBonusReward`, 56410).
- A boss is not counted at death: an actor with `extendedFlags` bit `$0080` is skipped by the counters (`StandardEnemyDefeatHandler.asm:38-58`, 56202-56242), the kill flag, the gem and the reward (the bit test at `:84-86`, 56297-56304, jumps to `EnemyDefeatBossCleanup`). The five boss lairs have tier 0 and no reward; the boss instead sets `playerFlags` bit `$0020`, which arms the catch-up (Q4).

**Q4: what is tested before the reward actor runs?** In `EnemyStatBonusReward` (`StandardEnemyDefeatHandler.asm:198-245`, offsets 56711-56816), in this order: (1) tier byte read and pushed (56714-56723); (2) `TestFlag_0300(sceneCurrent)` at 56727: set means `RewardNone` (Die, nothing spawns); (3) tier 0 at 56736-56738: `RewardNone`; (4) otherwise `displayModeFlags |= $0080` (56740, display-filter mode: only actors with `$12 $1000` run) and the pickup spawns with flags `$1000` and `$12 |= $1000` (tier 1 → `e_hp_increase` 56758, 2 → `e_str_increase` 56778, anything else → `e_def_increase` 56798). Before that, at the kill itself, the enemy is already dead and its kill bit set (`SetDungeonKillFlag`, 56306); `TestFlag_0300` at 56311 decides the gem (Q5).
**When the flag is set:** `RewardActorVFX` (`reward_actors.asm:93-115`, `SetFlag_0300` at 57679) runs first inside each stat actor (`CallNear RewardActorVFX` at 57400 / 57478 / 57553), after the rise, the hold and the flight to the player; the stat is added after it returns. So the flag is set when the pickup reaches the player, one step before the stat changes. The boss catch-up sets it at `boss_clear_reward_handler.asm:159` (50035) before adding the stat.

**Q5: gem rule.** After the kill flag is set, `TestFlag_0300` (56311): flag set → the gem path (stats byte +3, `EnemyGemDropRouter`); flag clear and `orbitAngle` 0 (the last enemy) → no gem ("the stat reward replaces it", 56317-56321); flag clear and enemies remain → gem path. In a tier-0 scene the flag never gets set, so its last enemy never drops a gem and never pays (16 scenes have enemies and tier 0, section 4).

**Q6: `field_reveal_object` (VERIFIED-STATIC, dead path).** The actor tests `$26` first (`field_reveal_object.asm:41-43`, 55941 / 55943): nonzero goes to `FieldRevealFromActorStats` (a gem). Only `$26 = 0` reaches `TestFlag_0300` (55948), the tier read (55957) and the stat items `$80-$82` (55980+). All three spawners copy the remaining count into the child's `$26` right after `SpawnAfterFlags` (`EnemyDefeatDispatch.asm:49-55`, `pyCC_mystic_ball.asm:194-196` {771837, 771844, 771848}, `awB1_wall_walker.asm:258-260` {769369, 769376, 769380}); the count is never 0 there because the last kill jumps to `StandardEnemyDefeatHandler`, and a `DEC` of 0 would wrap to `$FFFF`. Absence search: `rg "field_reveal_object" extracted/**/*.asm` returns spawns only in those three files (plus `?INCLUDE`s and comments); `scene_actors.asm` places it in no list; no COP-computed spawn can name it (the label appears in no operand elsewhere). So the room-tier path never runs: the shipped notes that say two spawners pass `$26 = 0` are wrong (section 8).

**Q7: boss catch-up (`boss_clear_reward_handler`).** The actor exists only in the five boss arenas (`$29` Castoth, `$55` Viper, `$67` Mu vampires, `$8A` Sand Fanger, `$DD` Mummy Queen; rows of `scene_actors.asm`; `tierscan` lists exactly those five). Flow: find `sceneCurrent` in `boss_reward_range_table` (4-byte rows scene / first / last-exclusive / pad: `$29: $0C-$28`, `$55: $3D-$54`, `$67: $5A-$66`, `$8A: $6D-$89`, `$DD: $A0-$DC`; rows 5-10 are placeholders), `TestWramFlag_Offset100(row / 4)` (49883; boss flags `$0500-$0504` = global 1280-1284, FL15), then poll `playerFlags` bit `$0020` (49891). Then `BossClearApplyStatReward` (49982-50070) walks the range: nonzero tier and `TestFlag_0300` clear → `SetFlag_0300` (50035), add the stat, continue. Afterwards `hpToHeal := maxHp - hp` and `SetWramFlag_Offset100(boss)` (49928). The latch `playerFlags |= $0020` is set by `LDA #$0020 / TSB $playerFlags` in exactly the five lairs: `ir29_castoth.asm:282` {695340}, `sg55_viper.asm:1102` {710995}, `mu67_vampires.asm:1250` {719477} and `:1282` {719548}, `gw8A_sand_fanger.asm:734` {755088}, `pyDD_mummy_queen.asm:497` {764376}. Scope of that search: `LDA #$0020` directly followed by `TSB $playerFlags` in all 909 `.asm` (other ways to set the bit, such as `ORA`, were not searched; who clears the bit was not searched).
All 87 table scenes lie in exactly one range (14 / 15 / 6 / 13 / 39 for bosses 0-4); no table scene is outside a range. Consequence: every nonzero room is paid either by its own last kill or by the boss catch-up, so no tier-1-3 room stays unpaid after its dungeon boss dies; a room whose flag is set by the catch-up stops showing the radar frame.

**Q8: what does the radar show?** `RadarScreenSetup` (`radar_map_screen.asm:170-214`): `TestFlag_0300(sceneCurrent)` at 229828 (set → no frame), then the table byte at 229837 (0 → no frame; the value is only tested for nonzero, so tiers 1, 2 and 3 look identical). Otherwise it writes a 4×4-cell frame (corner `$2EE1` with the three flip variants `$6EE1 / $AEE1 / $EEE1`, edges `$2EE2` and `$2EE3` with flips) around a 2×2 icon of tiles `$32E8-$32EB` (229930-229948) and runs the BG3 script `system_strings.consolestring_01EAD1` (229955), whose text is `[POS:C6,1][PAL:14]FORCE` (`tables/system_strings.asm:803`). The picture of tiles `$32E8-$32EB` was not decoded (runtime queue FL13-RADAR); that the icon does not depend on the tier is VERIFIED-STATIC (the only read of the table value is a zero test).

**Q9: scenes with a table row but no reward actor, and the reverse.**
- Reward actor never placed in a scene list: none of the three `reward_actors` and `field_reveal_object` is placed by any `scene_actors.asm` row (`tierscan`, "scenes that place a reward actor or field_reveal_object directly": none). They only spawn at runtime.
- Table scenes with no enemy row (the last-kill route cannot fire; only the catch-up pays): `$84` (tier 2, boss 3; no scene record, no warp entry names it) and `$CD` (tier 2, boss 4, `pyramid/puzzle_room`; one warp entry from `$CC`). 
- Table scenes whose last-kill route may not work: `$21`, `$23`, `$41`, `$B7` (a counted row whose actor script has no death path: frozen whirligig, bat spawner, sliding gate) and `$B0`, `$B6`, `$BA` (`awB0_zombie` rows whose death callback does not reach the counters in the code read). They stay INFERRED and are queued; the catch-up pays them in any case.
- The reverse (scenes with enemies, no reward): 16 tier-0 scenes with enemy rows: `$1B`, `$1F`, `$5C`, `$E8`, `$E9`, `$EA` (ordinary rooms and the comet / mansion / solid-arm lairs) and the ten boss arenas `$29`, `$55`, `$67`, `$8A`, `$DD`, `$F2`-`$F6`. Their last enemy neither pays nor drops a gem (Q5; for the boss arenas the boss itself is skipped by the counters).

## 3. Lifecycle

The flags live in the save block copied by `save_system.asm:57` / `:108`. Per FL12 (`ClearSceneState` zeroes only `$0A00-$0A01`, `ClearAllWramFlags` only `$0A80-$0A9F`) and the absence searches above (no clear wrapper exists for the `_0300` base), nothing clears them: a set bit stays for the life of the save. Kill bits (`wramFlags`, global `$0400-$04FF`, D6, FL10) are a separate dungeon-scoped store. A claimed room shows no reward frame, and any enemy it spawns takes the gem path (56311).
