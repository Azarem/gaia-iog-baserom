## Static answers

### OQ-19 (`BranchIfItemEquipped` with `inventoryEquippedIndex = $FFFF`)
Answer. The state is normal, not a corner case: `wram-init` sets index `$FFFF` at boot (`system_init.asm`, init entry `;20`: "wram-init < $inventoryEquippedIndex, #$FFFF >"), the inventory tab writes `$FFFF` when an empty slot is confirmed (`inventory_menu.asm` tags 189718/189733) and `RemoveItemFromInventory` writes it (`inventory_mgmt.asm` tag 258222). The handler loads Y 16-bit (`LDY` at tag 44132, x = 0 at COP entry) and does an 8-bit `CMP $inventorySlots,Y`: `$0AB4 + $FFFF` carries into the data-bank byte, so the read is bank `$82` (DBR is `$81`, `cop_dispatch.asm:7`) offset `$0AB3`, which is the WRAM low-RAM mirror, i.e. WRAM `$0AB3`, not an in-bank wrap. `$0AB3` is the high byte of the word `$0AB2` that `DarkSpaceMainInit` stores with a 16-bit `STA` (`sE6_gaia.asm` tag 579539, preceded by 3-byte `CMP #$0004` / `LDA #$0000`), value 0 to 3, so the high byte is 0. No other reference to `$0AB3` exists in `extracted/` or `baserom/` (rg for `$0AB3`: 0 hits; `$0AB2`: the Dark Space store at tag 579539, the diary load at tag 779271 and `NewGamePlus.patch.asm:74`). The five operands (`#27` at tag 629147, `#1C` at 563771/563789/563805, `#0F` at 382561) never equal 0, so with nothing equipped the branch is not taken, the intended result.
Evidence. `cop_handlers_inventory.asm` tags 44122-44161; sites above; `inventory_menu.asm:302-315`; `system_init.asm` (wram-init list).
Remains open. The byte actually seen at `$82:$0AB3` in a session (read breakpoint); whether a save/load block copy can leave a nonzero `$0AB3` (no writer found by name; a bulk copy is not excluded by rg). The shipped note says "wraps to `$0AB3`" and "analysis only, unverified at runtime": the outcome is right, the mechanism is the bank carry (spec text in `S1_notes.json`).

### OQ-21 remainder (`hdma_entry_stride_by_mode` entries 03-0C)
Answer. The only reader of the 13-byte table is `ParallaxResolveEntryStride` (`scanline_band_hdma_thinker.asm` tags 47802-47818): `LDA hdma_channel_config,Y; AND #$0007; TAY; LDA hdma_entry_stride_by_mode,Y`. Every one of the 64 bytes of `hdma_channel_config` (`hdma_ramp_tables.asm` lines 10-73: values `00,01,02` and `$80,$81,$82` for registers `$34-$3F`) has low three bits 0 to 2, and the table is ROM, so entries 03-0C (`05,05,64,00,FF,7F,FF,7F,FF,7F`) are unreachable. Coverage: rg for the label in `extracted/`, `baserom/`, `db-us/`, `docs/`: only the two uses above plus the definition and notes.
Remains open. What the `FF/7F` pattern is (data left in the ROM); not decidable from code.

### OQ-26 (range check of `MarkSolidOffset` / `ClearSolidOffset` / `*Abs` indices) - NOT SETTLED
Answer so far. The handlers do not range-check: they call `TileCoordsToMapIndex` and write `$7FC000,X` directly (`cop_handlers_collision.asm` tags 34978-35243; the header says so, line 9). The index is `(tileY>>4)*stride + (tileX>>4)` in the high byte (`map_coords.asm` tags 176291-176334), and the collision layer is `$4000` bytes, so a page number of 64 or more writes outside it. Largest operands of the 173 `MarkSolidAbs`/`ClearSolidAbs`/`ClearTypeAbs` lines (rg over `extracted/`): X `$72` (`btE0_crystal_gate_a`, tags 624411-624450), Y `$4C` (`pyD6_vader_barrier_*`, tags 574359-574679). Worst cases: Y `$4C` / X `$39` gives page `4*stride+3`, out of range only for stride 16 or more; X `$72` / Y `$38` gives `3*stride+7`, out of range only for stride 19 or more. A scene map that wide would not fit the 64 pages, so in-map operands are in range.
Not settled because the per-scene map width (page stride) and height of the scenes that hold these sites were not decoded (the maps are compressed, `scene_meta` carries pointers only), and the 31 Offset-op sites depend on the actor position at run time.
Remains open. Decode the map header of each scene with an Abs/Offset paint site, or log `X` after `TileCoordsToMapIndex` in a census run.

### OQ-I060-6 (four empty one-byte bundles `16D210`, `16D211`, `16D317`, `16D318`)
Answer. The engine never reads them. `LoadPaletteBundle` reads sub-entries of 6 bytes from the table pointer and stops at the first byte 0 (`hdma_dma_spc.asm` tags 254160-254166, `BEQ` on the frame count), resetting the sub-entry counter; the frame data is reached only through bytes 1-2 of a sub-entry. The bytes at `16D210/211` sit between the end byte of bundle `$77` (sub-entry at `palette_bundle_strip8_77`, `palette_bundles.asm` lines 10098-10102) and its frame array `word_16D212`, and the same for `$78` (`16D317/318`, frames at `word_16D319`). For comparison, bundle `$0B` has its frames immediately after the end byte (`palette_bundles.asm` lines 810-816, names `1476087` and `&word_1685FE`). No table pointer or sub-entry points at any of the four (rg for the labels: definitions and their own notes only).
Remains open. Why the ROM has two spare bytes after those two bundles (alignment or removed data): not decidable; "padding" stays an inference. The shipped notes already say "Not established: whether these bytes are padding" (`palette_bundles.asm` lines 10105, 10254). The inventory cluster PBUNDLE does not apply to this id.

### OQ-I070-1 (dictionary substitution rule in the rebuild)
Answer. The extractor expands dictionary references to text (`gaia-core/src/rom/extraction/writer.ts` lines 630-648) and the rebuild recomputes them (`gaia-core/src/rom/rebuild/string-processor.ts` lines 92-108): all entries of both dictionaries are flattened (`DbStringType.dictionaryLookup`, `database/strings.ts` lines 101-104, id = `(command << 8) | index`, so `$D6xx` for table A and `$D7xx` for table B), sorted by text length, longest first (stable sort: equal lengths keep table order, A before B), and for each word every occurrence is replaced anywhere in the string with no word-boundary test. A string that is exactly one dictionary word is not substituted (`fullMatch`), and strings with the raw flag skip the step. The replacement `[D605]`-style token is then encoded as two bytes (`string-processor.ts` lines 141-146). The word lists come from `db-us/stringTypes.json` (`dictionaries`, lines 131-397 and on, 456 entries), not from the dictionary data in `dialog_dictionaries.asm`.
Remains open. Whether the greedy longest-first result equals the original ROM bytes for every string is shown only by the rebuild gate (byte-identical build), not by this read; whether `stringTypes.json` and the ROM dictionary tables are kept in step if a patch edits one (not checked). The test with a changed word belongs to step T1.

The shipped notes already say this (`camera_tilemap.asm` block note, `scene_lifecycle.asm:924`, `docs/wram-memory-map.md:322`); `DialogStringRenderer.asm:142` was already handled (`docs/mesen2-c-series-summary.md:123`).

### OQ-I044-4 (does the A button feed the interact bit `$8000`?)
Answer. Yes. `system_init.asm` init entries `;19`-`;1C` set `remapB $4008`, `remapA $8080`, `remapY $0040`, `remapX $0004` (the shipped values; `db-us/transforms.json` lines 716-719 rewrite the vanilla `$8000 / $0080 / $4000 / $0040`). `VBlankWaitAndJoypad` ORs each remap word into `joypadRemapped` when its physical bit is held (`vblank_joypad.asm` tags 164069-164123): physical A (raw `$0080`) sets logical `$8000` (interact, confirm) and `$0080` (attack/action), physical B (raw `$8000`) sets logical `$4000` (cancel) and `$0008` (use item). ### OQ-I037-2 (does `COP LoopEnd` yield once per pass?)
Answer. It yields on every pass except the last: `LoopEnd` decrements the counter; at zero it continues with `RTI`; otherwise it restores the loop head into `$00` and yields with `RTL` (`cop_handlers_script_control.asm` tags 43790-43840). `LoopStart #10` is 16 passes (the operand is hex), so the 16-pass slides in `gw82_archer.asm` (tags 757860-757872, 757917-757929, 758001-758013, 758058-758070) yield 15 times; the 16 passes run in 16 consecutive frames and the code after the loop runs in the same frame as the last pass. The shipped `LoopEnd` note says "each iteration ends with a yield", which is wrong for the last pass (spec text in `S1_notes.json`).
Remains open. What happens when the player walks into the statue mid-slide (collision was moved by `MarkSolidHere` first, `$12` bit `$0010` set): runtime.

### OQ-I051-1 (`Layer1DriftUnbounded` integration tail every frame after `WaitByte`)

### OQ-I049-6 (drop probabilities; heal sparkle position)
Answer. The sparkle position is the pickup actor (see OQ-I042-1).
Remains open. That `RngByte` really covers 0-255 evenly and the tier thresholds at odd maximum HP: runtime.

### OQ-I060-3 (choice id mask `$1F`)
Answer. `StageWorldMapChoice` stores the byte unmasked (`AND #$00FF` only) into `$0D58` (`cop_handlers_world_map.asm` tags 40340-40347); `WorldMapController` keeps the full value in `$24` and masks the low 5 bits only for the `world_map_options` index (`WorldMapController.asm` tags 238380-238395). Staged ids are `$01-$1B` (`world_map_options.asm:34`; the `StageWorldMapChoice` sites in `overworld_exit.asm` list ids up to `#1B`), so the mask has no effect in the shipped game; an id of `$20` or more would run the entry of id minus `$20`.
Remains open. Nothing static (the "stage above `$1F` with a debugger" test is a runtime curiosity, not a shipped path).
