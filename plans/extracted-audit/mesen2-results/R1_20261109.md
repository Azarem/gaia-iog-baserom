## Observations

1. **Block moves read bytes that no routine parses.** In scene `$AA` a block move running from the WRAM mirror (`$82:0406`) reads 846315..846330 and 846406..846417 in sequence (X and Y +1, A -1 per byte). These are the all-bytes reads that first made `thinker_spawn_0CE9EA` and `0CEA45` look "touched" (17 and 13 bytes). The record loop of `SpawnSceneThinkers` reads only the first byte of each (the high byte of a 16-bit load across the previous list's `$FF`, pc `$83:D802/D812/D840/D846`). A read counter over a data range therefore needs the reader's pc before it counts as use.
2. **A 16-bit opcode fetch reads one byte past a script.** The 82 reads of ROM 56579 (first byte of `SpawnItemSparkleEffect`) are `LDA [$0A]` in `CopDispatch` (`cop_dispatch` tag 33913, pc `$80:847B`) fetching the COP signature at 56578 (the last COP of `SpawnDamageNumberEffect`) as a word. The same pattern is the likeliest source of the single read of `ForcedWalkWest` (60483); that one was not traced by a callback.
3. **`NorthProbeRedirect` pair is dead (5 of 5 entries).** At the entry and at `loc_02D208` the `$00` word, SP, D and DBR are equal; X (+`$10`) and A and the carry differ after the pair but `MapCellLeft` reloads X and A from `$00`. The shipped part note still says "Everything here is UNVERIFIED-RUNTIME" (see Notes spec).
4. **Ability name / description tables.** Status tab, form 0 reads `ability_name_table[01-03]`, form 1 `[05-07]`, form 2 `[09-0B]` and the matching description pointers: the index is form x 4 + slot + 1 with slots 0-2 (`[00]`, `[04]`, `[08]` of the name, menu and description tables and `ability_description_table[0C]` are never read; the 4 reads of the "`ability_name_table[0C]`" row are the string bytes of `BLACK4K`, Observation 5). The Shadow placeholder strings `DEFENCERK`, `DARKCOREK`, `BLACK4K` and 'Dark 1' are read in the form-2 probe, so they are reachable through the tab when the Shadow ability bits of `$0AA2` are set (`$7777` written in the probe; whether the game ever sets bits 8-10 was not checked).
5. **Range definition caveat.** The `ability_name_table[0C]` row is the first 2 bytes of the string `BLACK4K` and the rows `consolestring_01E655` and `consolestring_01E6D4` extend over the pointer tables that follow the string; their read counts mix string and table bytes (verdict INCONCLUSIVE for those two rows).
6. **Coverage depth.** Animation pointers selected: Will 40 of 72, Freedan 32 of 76, Shadow 28 of 76, `spriteset_will_abilities` 9 of 39, `spriteset_pickups_effects` 26 of 63, `spriteset_transform_poses` 15 of 19. The Will table's `$04`-`$07` and `$14`-`$17` were never selected by any of the 133 legs or the 20 probes; the unread Freedan and Shadow ranges `$1D`-`$29` and `$3E`-`$4B` need states (vine, ladder, ledge, flight) that the replays did not reach.

## Verdicts

Rule used: a zero count is VERIFIED-RUNTIME (negative) only when (a) the control rows of the same range family ran in the same legs, (b) the coverage statement above lists what was driven, and (c) my own pointer scan (`R1_static.txt`, the R3 method on ROM O) found no reference; otherwise a zero count is INCONCLUSIVE. Index tables (sprite animations, palette bundles, move chains): a pointer read proves the index is selected (VERIFIED-RUNTIME); a zero never proves absence because a stager can take the index from RAM (INCONCLUSIVE). Full per-range counters (1,099 ranges, exec / starts / read / write / CDL / top legs): `raw/R1_table.md`.
